# Level 5 — チームで（新人の受け入れ、共同作業、この手引き自体の保守）

> この章の「共同作業の規則」は、**研究室で運用しながら固めていく案**です。実際に運用して、合わなければ書き換えてください（このリポジトリ自体も Git で管理します）。

## ゴールの状態
- 新人が初日に、この手引きだけで環境を作れる（`bin/doctor.sh` が要修正 0）。
- 複数人が同じリポジトリを触っても、衝突せず、レビューが回る。
- 共有資源（サーバー）を、お互いを壊さずに使えている。
- この手引き自体が古くならず、直し方の手順がある。

## 2. 共同作業の規則（案）
個人の運用（手元とサーバーの2か所）では「編集する場所」を分けましたが、**複数人で同じリポジトリを触るとき**は、さらに「誰が何を変えているか」を分ける必要が出ます。
### 基本方針
1. **`main` には直接 push しない**。各自が `feature/<topic>` の枝で作業し、**Pull Request（PR）** で取り込む（[03 Git](../01-design/03-git.md) の枝のルール）。
2. **PR は他の人が1人以上レビュー**してから取り込む。
3. **各自が自分の clone を持つ**（手元とサーバーに、自分のホーム配下で）。他人のホームを触らない。
4. 枝の名前に自分の名前を入れて衝突を防ぐ案: `feature/<topic>`（個人の研究プロジェクト）、共有リポジトリでは `feature/<name>-<topic>`。
5. コミットメッセージは「何を・なぜ」を1行で（例 `Add noise model for VQE`）。

### 共有リポジトリ／共有データ
| 種類 | 置き場 | ルール |
|---|---|---|
| 研究室共通のコード・ツール | 研究室の GitHub 組織の private リポジトリ | PR 必須。READMEに目的と連絡先 |
| 個人の研究プロジェクト | 個人の GitHub（または組織内の個人リポジトリ） | 規則は個人の自由だが、構造は本手引きに合わせる |
| 共有データ（研究室で使い回す） | 共有ストレージの読み取り専用ディレクトリ | **書き換えない**。コピーして使う。出所と版を README に記録 |
| 秘密情報 | どこにも置かない | 鍵・トークンは各自のマシンのみ |

### サーバーを共有するときの作法
- 計算は**必ずジョブで**（[運用ルール](../03-operate/01-server-rules.md)）。
- 大規模に使う前は `your-channel` で相談。混む時期は譲り合い。
- 対話ジョブ・JupyterLab は、使い終わったら即開放。
- 他人のホーム・共有ディレクトリは、許可なく動かさない。

## 3. この手引き（`lab-workflow`）自体の保守
手引きは**生き物**です。次の流れで直します。
```text
気づいた → issue か PR（枝: feature/fix-...） → レビュー → main に取り込み → タグ（版）を打つ
```
### 3-1. 直し方
1. `git switch -c feature/fix-level2-typo`
2. 文書やスクリプトを直す。
3. **`tests/run.sh` を通す**（スクリプトの自動テスト）。
4. **`bin/render.sh --check`** を通す（個人情報・研究室固有の語の混入検査）。
5. PR を出して、レビューを受ける。
6. 取り込んだら、必要ならタグ（例 `v0.2.0`）を付ける。

### 3-2. 研究室固有の値の扱い（重要）
サーバー名・ユーザー名・チャンネル名などの**実際の値は、本文に書きません**。`your-cpu-server` のような**仮の名前**で書き、実際の値は `lab.conf`（Git に入れない）に置きます。`render.sh --lab` が、仮の名前を実際の値に置き換えた**研究室版のコピー**を別の場所に作ります（元は変わらない）。
```bash
cp lab.conf.example lab.conf && $EDITOR lab.conf     # example は書き換えず、lab.conf にコピーして編集
bin/render.sh --lab ~/lab-workflow-lab               # 研究室版（実値入り）を作る
bin/render.sh --check                                # 元のリポジトリに実値が混入していないか検査（PR の前は必須）
```
研究室で配る版は、この `lab-workflow-lab` を研究室の private リポジトリにします。**元のリポジトリを直した内容を研究室版に取り込む**ときは、元を更新して、もう一度 `render.sh --lab` で作り直します。

### 3-3. 公開するとき（チェックリスト）
- [ ] `bin/render.sh --check` が通る（個人名・メール・IP・研究室固有名が無い）
- [ ] **過去のコミット履歴を持ち込まない**: `bin/make-public-snapshot.sh` で履歴なしのコピーを作り、**新しい**リポジトリへ push する（既存の private を public に切り替えない）
- [ ] 作ったコピーを目で確認した
- [ ] 他人の著作物（引用、図）の出典とライセンスを確認した
- [ ] `LICENSE`（既定は MIT。ほかにしたい場合は変更）と `CONTRIBUTING.md` を確認した
- [ ] 新人（外部の人）に通しで試してもらい、詰まりを直した
- [ ] **実機で未検証の箇所**（鍵の方式 B・C、Mac）に「未検証」の表示が残っている

### 3-4. 保守担当
- 版の管理（タグ付け・公開版の生成）の担当者を決める（**未決定: 研究室で決める**）。
- 年度の変わり目に、「サーバーの構成・スケジューラ・VPN・相談先」が変わっていないか見直す。
