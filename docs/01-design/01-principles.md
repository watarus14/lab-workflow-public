# 01 原則と全体像

## この運用が解く問題
研究では、**手元のPC**（文章・コードを書く）と**計算機サーバー**（重い計算を回す）の2か所で、同じプロジェクトを扱います。放っておくと次のことが起きます。

- 同じファイルが2か所にあり、どちらが最新か分からない
- 両方で編集して、片方の変更が消える
- 結果が「どのコードで出たのか」分からなくなる
- ホームがごちゃごちゃで、何がどこにあるか分からない

この運用は、**ファイルの置き場所と運び方に決まりを作って**、これらを防ぎます。

## 理想の状態（先に完成形を見る）
```text
手元(WSL/Mac)                    GitHub                  計算機サーバー
~/projects/<project>/  ⇄ (中継・バックアップ) ⇄  ~/projects/<project>/
  コード・文章を書く                                        notebook を動かし、計算を回す
  結果を保管する  ◀──────── rsync（結果・データ） ────────  runs/ に結果が出る
```
- 同じ名前のプロジェクトが両側にある。
- **コードは git、データ・結果は rsync** で運ぶ。
- 実行ごとに記録（`run_id`）が残り、結果から元のコードに戻れる。

## 5つの原則
| # | 原則 | 具体的には |
|---|---|---|
| 1 | **置き場所は1つ** | 1つの物の「正本」は1か所。ファイルごとに「編集する場所」を決める |
| 2 | **運ぶ道具は種類で決める** | 小さく履歴が要るもの→git、大きく履歴が不要→rsync |
| 3 | **確認してから実行、消さずに動かす** | `-n`（予行）を先に。削除は最後に、人が判断 |
| 4 | **秘密は持ち歩かない** | 秘密鍵は手元だけ。サーバーには置かない |
| 5 | **再現できる記録を残す** | 実行ごとに「どのコード・設定で出たか」を保存 |

## 「編集する場所」を決める、とは
**これは「誰が担当か」の話ではありません。** あなた1人でも、同じプロジェクトが手元とサーバーの2か所にあります。同じファイルを**両方の場所**で編集すると、あとで git が「どちらを採用するか」を判断できず衝突します（これが「相手側の領域」＝*自分のもう一方の場所*という意味です）。

だから、**ファイルの種類ごとに「編集するのはこちらの場所」と決めます**。決め方の基準は「そのファイルを編集するのに、何が必要か」です。

| ファイルの種類 | 編集する場所 | 理由 |
|---|---|---|
| `notebooks/`（Jupyter） | **サーバー** | 計算環境（カーネル）が要る。手元に環境を作らなくて済む |
| `src/` `scripts/` `config/`（コード・設定） | **手元** | 実行しなくても書ける。好きなエディタで書ける |
| `paper/` `docs/`（文章・メモ） | **手元** | サーバーでは読む必要もない。GitHub を経由して保管されるだけ |
| `runs/`（計算結果・ログ） | サーバーで生成 | 人は編集しない。手元に回収して保管するだけ |

> 「サーバーのファイルをVS Code(Remote-SSH)で開く」のは、画面は手元でも**ファイルの実体はサーバー**。つまりサーバーで編集しています。
> **どちらが正しいかは問題ではありません。問題は「同じファイルを両方で編集すること」だけです。**
> サーバーで `.py` を直したくなったら、手元で直して送る。緊急でサーバーで直したら、すぐ commit・push して手元で pull する。

チームで開発する場合（複数人が同じリポジトリを触る）は、各自が自分のブランチで作業し、Pull Request で取り込みます（Level 5）。

## 運び方の全体表
| 種類 | 正本 | 向き | 道具 | Git管理 |
|---|---|---|---|---|
| コード・設定（`src/ config/ scripts/`） | 手元 | 手元 → GitHub → サーバー | **git** | ○ |
| notebook | サーバー | サーバー → GitHub → 手元 | **git** | ○ |
| 論文・文書（`paper/ docs/`） | 手元 | 手元 → GitHub（サーバーへは不要） | **git** | ○ |
| 採用した図 | サーバーの結果 | 手元で `results/` から `paper/figures/` へコピー | `pick-figure.sh` | ○（小さい図のみ） |
| 計算結果・ログ | サーバー | サーバー → 手元 | **rsync** | ✕ |
| 入力データ（サーバーで取得・生成） | サーバー | サーバー → 手元（バックアップ） | rsync | ✕ |
| 入力データ（手元発） | 手元 | 手元 → サーバー | rsync | ✕ |
| 秘密情報（鍵・トークン） | 各自のマシン | **転送しない** | — | ✕（絶対） |

## 設計の方針（補足）
- **Git管理するか否かで、トップ階層を分ける**: Git管理（`src notebooks config scripts docs paper`）／管理外（`data runs results`）。
- **トップ階層は10個以内**。ルート直下にファイルをばら撒かない。
- **サーバー識別子は1つに統一**: `~/.ssh/config` の `Host` 名 ＝ `config/<名前>.yml` ＝ `results/<名前>/`。名前が揺れると自動化できない。
- **1プロジェクトの編集サーバーは1台**。複数台で走らせるなら、編集は主サーバーだけで、他は `git pull` のみ。
